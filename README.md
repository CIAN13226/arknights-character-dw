# arknights_dw · 明日方舟干员数据仓库

用 PRTS 的干员数据，按维度建模的方式搭一个分层数据仓库。
数据源是同一个仓库里的 RAG 项目（`../rag_project`），这里不重新抓取，只做建模和分层。

**当前进度：模型设计完成，7 张表的 DDL 已建，`dim_phase` 已灌。其余表待灌数据。**

---

## 这是什么

一个练习用的数据仓库：从游戏 wiki 抓 463 个干员的 **wikitext 原始源码**，按 ODS / DWD / DWS / ADS 四层建模，最后产出能直接喂看板的势力排行和职业画像。

目标是把"一堆带模板语法的 wiki 源码"变成"能按维度切、能算指标、口径说得清"的结构化数据。

数据规模：

| 项 | 数值 |
|:---|---:|
| 干员 | 463 |
| 结果数据总行数（16 张表） | 7,983 |
| 干员属性快照（事实行） | 1,796 |
| 势力归属记录 | 668 |
| 模组记录 | 513 |
| 标签记录 | 819 |
| 潜能加成记录 | 2,155 |

## 项目亮点

- **四层分层全部落地。** ODS 463 → DWD 6,418 → DWS 1,060 → ADS 42，16 张表共 7,983 行。
  **每层只读上一层**，并且全部可由 6 个脚本从零重建——仓库里没有一个数据文件。
- **从原始 wiki 源码开始解析。** ODS 存的是 463 份 wikitext 原文（592 万字符，含模板语法、未做任何加工），
  DWD 自己解析。数仓不依赖任何上游项目的中间产物。
- **建模决策有数据依据，不靠经验。** 实测发现 **34 个干员的阻挡数、446 个干员的部署费用会随精英阶段变化**，
  所以它们归入事实表而不是维度表；等级上限是 2★=30 / 3★=40,55 / 6★=50,80,90，不是固定的三档。
- **汇总层只存可加度量。** DWS 里没有任何一列平均值，全是 `sum` + `count`——
  因为平均值不可再聚合。平均值、排名这类成品值只出现在 ADS，
  **不可加度量只允许存在于链路终点**。
- **有可重复执行的质量门禁。** 45 项校验（行数基线 / 主键唯一性 / 外键完整性 / 跨层一致性 / 取值合理性），
  有不通过就退出码 1，可直接挂到调度上。散落在构建脚本里的校验只是"当时那批"的快照，这个是全量体检。
- **缺陷和修复过程都记录在案。** `join` 多个多值维度会让指标静默放大 2.15 倍；
  Spark 4 的中文列别名必须加反引号（`ORDER BY` 里的引用也要加）；`insertInto` 是按列位置匹配的。
  这三条都写了成因和验证方式。

## 模型设计

**雪花模型**：1 张事实表 + 6 张维度表。

```
        ┌──────────────┐   ┌──────────────┐   ┌──────────────┐   ┌──────────────────┐
        │  dim_faction │   │  dim_module  │   │   dim_tag    │   │  dim_potential   │
        │     (N)      │   │     (N)      │   │     (N)      │   │       (N)        │
        └──────┬───────┘   └──────┬───────┘   └──────┬───────┘   └────────┬─────────┘
               │                  │                  │                    │
               └──────────────────┼──────────────────┼────────────────────┘
                                  │ 箭头指向 ↓
                       ┌──────────▼───────────┐
                       │    dim_operator      │
                       │        (1)           │
                       └──────────▲───────────┘
                                  │ 箭头指向 ↑
                       ┌──────────┴───────────┐
                       │  fact_operator_attr  │
                       │        (N)           │
                       └──────────┬───────────┘
                                  │ 箭头指向 ↓
                       ┌──────────▼───────────┐
                       │      dim_phase       │
                       │        (1)           │
                       └──────────────────────┘
```

### 表清单

DWD 层 7 张表：

| 表 | 类型 | 主键 | 一行代表 | 行数 |
|:---|:---|:---|:---|---:|
| `dim_operator` | 维度 | `operator_name` | 一个干员 | 463 |
| `dim_phase` | 维度 | `phase_id` | 一个精英阶段档位 | 4 |
| `dim_faction` | 维度（多值） | `(operator_name, faction_name, relation)` | 一个干员的一个势力归属 | 668 |
| `dim_module` | 维度（多值） | `(operator_name, module_name)` | 一个干员的一个模组 | 513 |
| `dim_tag` | 维度（多值） | `(operator_name, tag)` | 一个干员的一个标签 | 819 |
| `dim_potential` | 维度（多值） | `(operator_name, potential_level)` | 一个干员的一个潜能加成 | 2,155 |
| `fact_operator_attr` | **事实** | `(operator_name, phase_id)` | 一个干员的某阶段属性快照 | **1,796** |

ODS / DWS / ADS 三层的表见「[项目结构](#项目结构)」里的数据流图，各表设计原则见对应章节。

### 为什么是雪花而不是星型

星型要求"每个维度表都直接描述事实"。势力、模组、标签描述的是**干员**，不是**某次属性快照**，所以它们只能连 `dim_operator`。一旦出现"维度表 → 维度表"的连线，就是雪花。

想做成纯星型只有两条路，都不划算：

| 路 | 做法 | 代价 |
|:---|:---|:---|
| 压成数组列 | 势力/模组/标签各存一个 `ARRAY<STRING>` | 失去精确筛选，"哪个势力人最多"要 explode 才能算 |
| 塞进事实表 | 事实表加 faction 列 | 粒度被污染：1,796 行涨到 5,000+，且 hp/atk 重复 |

### 几个建模决策

**① 维度 vs 事实的判据是"能不能求和/求平均"，不是"描述抽象还是描述动作"**

星级是数字但不能求和 → 维度表。部署费用能求平均 → 事实表。

**② 一个干员有多个值 → 拆成多行，不是加多列**

势力、模组、标签、潜能都是这个道理。用 `level1/level2` 两列装不下"凯尔希同时属于罗德岛和巴别塔"这种情况。

**③ 阻挡数和部署费用属于事实，不属于维度**

实测：**34 个干员**的阻挡数随精英阶段变（如百炼嘉维尔 `2→2→3`），
**446 个干员**的部署费用会涨（分布：1 段 17 个、2 段 343 个、3 段 103 个）。
其余属性（攻击间隔、再部署时间）全库都是单值，放维度表。

**④ 等级上限放维度表，不按固定规则**

上限随星级变，不是固定的 50/80/90：

| 干员 | 星级 | E0 | E1 | E2 |
|:---|:---|:---|:---|:---|
| 巡林者 | 2 | 30 | — | — |
| 芬 | 3 | 40 | 55 | — |
| 星熊 | 6 | 50 | 80 | 90 |

**⑤ 初始模组不进表**

`初始模组名`（如「星熊证章」）只有名字没有属性数据，是默认栏位。

## DWS 层：只存可加度量

### 为什么只存 sum/cnt，不存平均

**核心原则：平均值不可再聚合。**

假设 DWS 里按星级存了平均攻击：五星 600、六星 700。
想算「整体平均攻击」，写成 `(600+700)/2 = 650` 是**错的**。
正确值是加权平均——如果五星 300 人、六星 26 人，应该是
`(600×300 + 700×26) / 326`。**除非同时知道每组的人数，否则还原不回来。**

所以表里存 `atk_sum` + `atk_cnt`，平均用 `SUM(atk_sum) / SUM(atk_cnt)` 现算，
**任意层级都算得对**。

实测验证：用 DWS 现算的各职业精英2平均攻击，与直接从 DWD 算的结果**完全一致**
（狙击 765.8 / 近卫 755.9 / 术师 721.3 …）。

### 汇总表对账的两个坑

**① 不能拿全表求和去和明细表比 —— 口径不同**

`dws_faction_star` 只覆盖「有一级势力」的干员（434 / 463），
且势力是多值维度（一个干员可属多个势力，会在每处各计一次）。

**正确做法是同口径对账**：挑一个具体势力，把它在 DWS 的合计
和「从 DWD 按同样筛选条件算出来的合计」比。

实测（罗德岛）：DWS 攻击合计 = **133,790**，DWD 同口径 = **133,790** ✅

**② 单值维度可以严格对账，多值维度不行**

`profession` 是单值，一干员一职业，join 不放大，所以能整表对账：

| | DWS | DWD |
|:---|---:|---:|
| 人数合计 | 1,796 | 1,796 ✅ |
| 攻击合计 | 809,984 | 809,984 ✅ |

### 数据完整度（`dws_operator_completeness`）

这张不算业务指标，是**数据治理**用的：一行一个干员，记录 `dim_operator` 的
12 个描述字段缺了几个，以及各多值维度有没有数据。

实测：

| 项 | 值 |
|:---|---:|
| 缺失字段总数 | 220 |
| 有缺失的干员 | 60 / 463 |
| 有势力 / 有标签 | 434 / 463 |
| 有模组 / 有潜能 / 有信赖 | 398 / 431 / 452 |

**缺失最多的是那几个 1 星机器人**（CONFESS-47、Castle-3、Lancet-2…），
各缺 6 个字段——它们本来就没有种族/出身地/生日这类人设信息。
**这符合预期，不是数据错误。**

## ADS 层：成品值只允许出现在最后一层

DWS 不存平均值、ADS 却存——这个区别不是随意的：

> **DWS 的下游还要再聚合**（可能按势力汇总、也可能跨星级汇总），
> 平均值一旦存死就还原不回来。
> **ADS 是链路终点**，直接喂报表/看板，没有下游再算一次，所以存成品值是对的。
> 一句话：**不可加度量只允许出现在最后一层。**

## 数据质量校验（`05_quality_check.py`）

散落在各构建脚本里的校验只是"当时那一批"的快照。这个脚本是**可重复执行的全量体检**：
数据重跑、上游变了、有人手工改了表，跑一遍就知道库还是不是好的。

**45 项检查，分 6 类：**

| 类别 | 检查内容 | 项数 |
|:---|:---|---:|
| 行数基线 | 16 张表的行数必须等于已知基线 | 16 |
| 主键唯一性 | 每张表的主键组合不许重复 | 10 |
| 外键完整性 | 事实表/多值维度里的 operator_name、phase_id 必须能查到 | 6 |
| 跨层一致性 | ODS 与 DWD 的干员集合必须完全相同（双向） | 2 |
| 取值合理性 | 星级 1-6、属性为正、关键字段非空、阶段档位 1-4 等 | 10 |
| ADS/DWS 一致性 | ADS 的成品平均值必须等于 DWS 的 sum/cnt 现算值 | 1 |

**有不通过则进程退出码 1**，可以直接挂到调度里当质量门禁：

```powershell
python scripts\05_quality_check.py
if ($LASTEXITCODE -ne 0) { Write-Error "数据质量门禁未通过，中止下游任务" }
```

实测：**45 项全通过，退出码 0。**

## 示例查询

### 1. 跨三张表：各一级势力的六星人数与精英2平均攻击

```sql
WITH fac AS (
  SELECT operator_name, faction_name FROM dim_faction
  WHERE relation='所属' AND faction_level=1        -- 只取一级势力，避免和二级重复计数
),
six AS (SELECT operator_name FROM dim_operator WHERE star=6),
attr AS (SELECT operator_name, atk FROM fact_operator_attr WHERE phase_id=4)
SELECT fac.faction_name, COUNT(*), ROUND(AVG(attr.atk),1)
FROM fac JOIN six ON fac.operator_name=six.operator_name
         JOIN attr ON fac.operator_name=attr.operator_name
GROUP BY fac.faction_name HAVING COUNT(*) >= 3
ORDER BY COUNT(*) DESC;
```

实测结果（部分）：

| 势力 | 六星人数 | 平均攻击 |
|:---|---:|---:|
| 罗德岛 | 26 | 661.8 |
| 哥伦比亚 | 13 | 613.4 |
| 炎 | 11 | 625.5 |
| 维多利亚 | 11 | 583.0 |
| 乌萨斯 | 4 | **1116.5** |
| 巴别塔 | 4 | 941.0 |

### 2. ⚠️ 一个必须知道的陷阱：join 多值维度会放大指标

**这是数仓里最常见、也最不报错的一类 bug。**

想算「罗德岛六星干员的模组加攻总和」：

```sql
-- 正确：只 join 必要的表
WITH rop AS (SELECT DISTINCT operator_name FROM dim_faction
             WHERE relation='所属' AND faction_name='罗德岛')
SELECT COUNT(*), SUM(m.bonus_atk)
FROM dim_module m
JOIN rop ON m.operator_name = rop.operator_name
JOIN dim_operator o ON m.operator_name = o.operator_name
WHERE o.star=6 AND m.bonus_atk IS NOT NULL;
-- 结果：43 条，加攻总和 2989
```

**如果再多 join 一个多值维度 `dim_tag`（看起来无害，只是想顺便带个标签）：**

```sql
... JOIN dim_tag t ON m.operator_name = t.operator_name
-- 结果：93 条，加攻总和 6418   ← 行数和总量都被放大了 2.15 倍
```

**原因**：一个干员有多个标签，join 后每个模组行被复制了「标签数」次。
`COUNT` 和 `SUM` 全部翻倍，而且**不报错、结果看着也像正常数字**。

**规避办法**：一张事实表/多值维度，**不要在同一个查询里同时 join 多个 1:N 的多值维度**。
需要多个维度的信息时，先分别聚合到干员粒度，再在干员粒度上 join。

## 已知限制

- **部署费用"2 段"的 E1 值有歧义。** 源数据只给了链式值（凯尔希 `18→20`），
  这是"涨价前→涨价后"两个端点，没法确定 E1 是 18 还是 20。
  当前按 **E1 = E2 = 第二个值** 填充（依据：3 星干员只有 E0/E1 两个阶段，
  其 `9→11` 的第二个值只能是 E1，说明链的第二个值是涨价后的值）。
  **321 个干员受影响**（3 个精英阶段 + 2 段费用）。
  验证方法：游戏里看凯尔希精英1 时部署费用显示 18 还是 20。
- **潜能的天赋类加成无数值。** 源数据里这类位置是空字符串（表示"特殊效果"），
  表里用 `is_special = true` 标记，具体增强幅度没有存。
- **隐藏势力的层级信息丢失。** 隐藏势力有两种写法（`;;` 并列 / 逗号层级），
  拆开后无法区分，所以 `dim_faction` 里隐藏势力的 `faction_level` 一律为 NULL。
  查"谁算某势力"不受影响（只用 `faction_name`）。
- **属性类指标固定用精英2满级口径。** 不同阶段数值无可比性，
  ADS 里统一取 `phase_id = 4`。低星干员没有精英2，因此 ADS 的人数
  （如罗德岛 65）小于 DWD 里的归属人数（94）。**不同口径不能混着比。**
- **势力是多值维度，跨势力求和会重复计数。** 一个干员若属多个势力，
  会在每个势力下各计一次。看"全库总人数"要用 `dim_operator`。
- **没有做缓慢变化维（SCD）。** 当前数据是一次性快照，没有历史版本。
  ODS 里的 `etl_date` 已经为将来做 SCD 留了位置，但还没实现。
- **没有接调度。** 现在是手工按顺序跑 5 个脚本，还没上 Airflow / DolphinScheduler。
- **只覆盖明日方舟一款游戏。** 换游戏需要重写抓取和解析。
